# 上流の変更で再確認が要る成果物を知り、人の確認を記録する

## 使われ方

上流の成果物が変更されると、利用者は、その変更を踏まえた確認がまだ済んでいない下流の成果物を、
再確認待ちとして報告で受け取る。利用者は報告された成果物を 1 つずつ読み直し、内容を変える
必要があるかを判断する。変える必要があれば、人間が、または AI を活用したワークフローで内容を
更新する。内容を変えないという判断を含め、確認を終えたら、人間がその確認を item に記録して
コミットする。

確認する item を指定せずに始めることもできる。そのときは利用者が対話で枝を選び、上流から順に item を
読みながら人の確認を記録していく。

上流の変更は、下流のすべての成果物を変えることを意味しない。関係する下流の判断を見直す
必要が生じたことを意味する。製品はこの見直しの義務を可視化し、結果は人間が判断する。

利用者は `solution` と `use_case` を確認の問いで読み直し、方向性や要求がずれていないかを確かめる妥当性確認を
行う。製品は確認を記録する前にその型に当てる確認の問いを示し、人の確認を持たない `solution` と `use_case` を
報告する。また、item に `stale_after` で決めた見直しの期限が過ぎると、利用者は上流の変更が無くてもその item を
期限切れとして報告で受け取る。

## この使われ方が要求すること

- relation と item の記録から、上流の変更を踏まえた確認が済んでいない下流の item を検出できる
  こと。
- 検出した item を、人間による確認の対象として報告できること。
- まだ人間が確認していない成果物を報告できること。
- 人間が確認したことを item に記録でき、その記録をバージョン管理できること。
- 内容を変えないという判断も、確認として記録できること。
- 確認する item を指定せずに始め、対話で枝を選んで、上流から順に item を読みながら人の確認を記録できること。
- AI などが生成・更新した内容と、人間が確認した内容を区別できること。
- 再確認が要ることを示すだけで、内容を変えるかどうかを製品が決めないこと。
- `solution` と `use_case` の妥当性確認で、確認を記録する前に確認の問いを示せること。
- 人の確認を持たない `solution` と `use_case` を報告できること。
- `stale_after` の期限が切れた item と、期限が型ごとに決めた間隔より先に置かれた item を報告できること。
- 設定で伝播させると宣言した独自の relation も、再確認待ちの判定で辿れること。
- item を生成・更新した者を `generated.by` として item に記録でき、人の確認の記録と分けて読めること。
