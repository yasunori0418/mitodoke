# 設定ファイルは作業ディレクトリのものだけを読み、読んだパスを info に記録する

- ステータス: stable
- 日付: 2026-11-17
- 関連: GitHub Issue #4
- 起点: 2026-11-17 の grilling（Q46・Q49）で確定

## 背景

mitodoke の `--json` は、outturn の §8 の `standalone` まで含めて適合させると決めた。§8 は、
入力を stdin の JSON か明示した引数だけにし、設定を暗黙に探さないことを求めている。一方で
mitodoke は設定ファイルを読み、環境変数も読むことにしていた。

outturn の仕様と schema には、作業ディレクトリを表す標準のフィールドは無い。エンベロープの
トップレベルの `info` は、主体に紐づかない実行全体のツール固有の情報の置き場で、作業ディレクトリや
読んだ設定ファイルのパスを載せられる。実行の相関キーを規格に加える似た相談（outturn #18）は、
「規格の語彙にはしないが、ツールが `info` に載せるのは自由」として見送られた。作業ディレクトリの
フィールドを加え、§8 を「探索する場合は起点と解決した入力を記録する」と整合させる案は、outturn
#66 として起票した。

設定ファイルと環境変数を、`standalone` に照らしてどう扱うかを決める必要があった。

## 決定

`--config` を省いたときは、作業ディレクトリの設定ファイルを読み、上のディレクトリへは探さない。
実行時の作業ディレクトリと、読んだ設定ファイルの絶対パスを、エンベロープのトップレベルの `info`
に記録する。outturn #66 で規格のフィールドができたら、そちらへ移す。環境変数
`MITODOKE_GENERATED_BY` は引き続き読む。

## 根拠

実行時の作業ディレクトリと読んだ設定ファイルが出力に残れば、設定ファイルを探す作りでも、同じ
条件で実行し直せる。そうすれば、outturn の共通の結果の形の効果も活かせる。今の仕様の範囲でも
`info` に載せられるので、#66 の結論を待たずに進められる。

上のディレクトリへ探さないのは、作業ディレクトリ 1 つを記録すれば読む場所が決まり、再現の
手がかりが単純になるからである。

この形は §8 の文言どおりではない。outturn に適合していると言えるかは、#66 の結論で決まる。

## 棄却した代替案

### §8 の文言どおりにする

設定ファイルを `--config` で必ず受け取り、作業ディレクトリからは探さず、環境変数も読まない案。
解釈を挟まずに §8 に沿える。作業ディレクトリと読んだ設定ファイルを出力に記録すれば、探す作りでも
再現できるので、探索をやめる理由にならない。

### #66 の結論が出るまでは §8 の文言どおりにする

結論が出るまでは `--config` を必須にして環境変数を読まず、結論に合わせて緩める案。#66 の結論
しだいで、あとから呼び出し方を変えることになりうる。
