# 検査・起票・生成を 1 つの CLI のサブコマンドとして持つ

- ステータス: stable
- 日付: 2026-11-17
- 関連: GitHub Issue #4
- 起点: 2026-11-17 の grilling（Q1）で確定

## 背景

mitodoke は、文書の契約と関係を検査し、item を起こし、index.md などを生成する道具として
作る。手本にした文書管理の仕組みでは、これらの検査と生成が複数の shell script に分かれていた。
script は sara・git・jq と yq などの外部ツールを呼び、frontmatter の読み方も script ごとに
分かれていた。

「別の言語で CLI を作り、各契約を守るツールを呼び出す」という当初の構想を文字どおりに読むと、
CLI は振り分けだけを行い、契約ごとの独立した実行ファイルを呼ぶ形になる。製品の形を決める
前に、検査をどこに持つかを決める必要があった。

## 決定

1 つの CLI が、契約ごとの検査をサブコマンドとして内部に持つ。外部ツールに任せるのは、
すでに専用の仕事をしている sara と git などに限り、shell script の検査は CLI の中へ移す。
サブコマンドごとに入力・出力・exit code を定め、外から組み合わせられるようにする。

## 根拠

どの検査も、同じモデル・設定・frontmatter を読む。1 つの CLI に持てば、読み込みを 1 か所に
まとめられ、script ごとに分かれていた読み方がそろう。適用先の製品へ配る物も 1 つで済む。

concept §11-9 の「明確な契約と組み合わせ可能なツールを優先する」は、サブコマンドごとに
入力・出力・exit code を定め、外から組み合わせられるようにすることで満たす。§4.4 の
「外部ツールで足りる所はそれを使う」に沿って、すでに専用の仕事をしている sara と git などは
CLI の中に取り込まない。

## 棄却した代替案

### CLI は振り分けだけを行い、契約ごとに独立した実行ファイルを呼ぶ

当初の構想を文字どおりに読んだ形。どの検査も同じモデル・設定・frontmatter を読むので、
実行ファイルを分けても読み込みの部品は共有することになる。分けた分だけ、配る物と
バージョンの組み合わせが増える。

### CLI を新しく作り、中では既存の shell script を当面そのまま呼ぶ

移行の途中の形。script ごとの読み込みがそのまま残るので、読み込みを 1 か所にまとめて
読み方をそろえる利点が得られない。
