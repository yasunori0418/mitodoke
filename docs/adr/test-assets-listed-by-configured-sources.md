# テスト資産の列挙は内蔵せず、設定のコマンドかコミットしたファイルから読む

- ステータス: stable
- 日付: 2026-11-17
- 関連: [test_case の target を resource に改名する](test-case-resource-field.md), GitHub Issue #4
- 起点: 2026-11-17 の grilling（Q23・Q27）で確定

## 背景

テストケースとテスト資産の 1:1 を確かめるには、テスト資産の一覧が要る。テストの列挙の方法は、
言語とテストフレームワークによって変わる。コンセプト文書の §10 は、特定のプログラミング言語や
テストフレームワークを核のモデルの一部として押し付けることを非目標に挙げ、§5.3 は、テストケースと
テストコードのファイルや resource の 1:1 を「プロジェクトの契約で定める」と書いている。

この一覧をどう用意するかと、用意の仕方を同じ適用先の製品で併用できるかを決める必要があった。

## 決定

`mitodoke` はテスト資産の列挙を内蔵しない。

- 適用先の製品が設定に列挙のコマンドを書き、`mitodoke` はその出力を読む。出力は 1 行に 1 つのテストで、タブ区切りの `<資産識別子>\t<種別>\t<テスト名>`（テスト名は空でもよい）。資産識別子はテストケースの `resource` と同じ表記にする
- 選択肢として、適用先の製品がコミットした一覧のファイルを読むこともできる。ファイルの形式はコマンドの出力と同じタブ区切りの 3 列にする
- 列挙のコマンドとコミットしたファイルは、同じ適用先の製品で複数書いて併用できる。すべてを合わせて 1 つの一覧にし、同じ資産識別子が 2 か所から出たら失敗にする
- 対象から外す資産と、その理由も設定に書く

一覧の読み方の規範は [テスト資産の一覧は設定のコマンドとファイルから読み、併用した一覧の重複は失敗とする](../requirements/test-asset-inventory-sources.md) が定める。

## 根拠

- 列挙の方法は言語とテストフレームワークで変わるので、`mitodoke` が列挙を持つとコンセプト文書の §10 の非目標に当たる
- コマンドで列挙すれば、判定のたびに一覧を取り直すので、一覧が古くならない
- 出力を 3 列にすれば、1:1 の判定と対応表の両方を 1 つのコマンドで賄える
- 一覧を出すのが難しい言語・ライブラリにも対応できるように、ファイルを読む選択肢を加えた
- コマンドとファイルを併用できれば、複数の言語を使うリポジトリで、出せる部分はコマンドで、出しにくい部分だけをファイルで管理できる。ファイルが古くなりうる範囲も、その部分だけで済む
- 同じ資産識別子の重複を失敗にするのは、2 か所で同じ資産を数えると、テストケースとの 1:1 の判定が狂うからである

ファイルを読む選択肢には、テストを追加したり消したりしたあとに一覧の更新を忘れると、1:1 の判定が古い一覧で
成功しうるという弱点がある。一覧を出しにくい言語・ライブラリへの対応を優先して、この弱点を受け入れた。
列挙のコマンドに要るツールは、CI でも適用先の製品が用意することになる。

## 棄却した代替案

### mitodoke が主な言語のテストの列挙を内蔵する

`mitodoke` が Rust や Go など主な言語のテストの列挙を内蔵する案。列挙の方法は言語とテストフレームワークで
変わるので、コンセプト文書の §10 の非目標に当たる。このため採らなかった。

### コマンドだけを読む

設定に書いた列挙のコマンドの出力だけを読み、ファイルは読まない案。一覧が古くならない利点があるが、一覧を
出すのが難しい言語・ライブラリに対応できないので採らなかった。

### コミットしたファイルだけを読む

適用先の製品が資産の一覧をファイルに書いてコミットし、`mitodoke` はそのファイルだけを読む案。テストを
追加したり消したりしたあとに一覧の更新を忘れても、1:1 の判定が古い一覧で成功してしまうので採らなかった。

### コマンドとファイルのどちらか一方だけを書く

設定には、コマンドかファイルのどちらか 1 つだけを書く案。複数の言語を使うリポジトリで一部の言語だけ一覧を
出しにくいとき、コマンドを諦めてすべてをファイルで管理することになるので採らなかった。
