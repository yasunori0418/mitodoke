# term-record: 決まった用語を台帳へ記録する

議論の中で語を研ぎ、決まった語を**台帳**に書き留める。台帳は item の材料で、item そのものではない。
item にしてコミットするのは `/term-apply` で、PR を作る前に利用者が明示で起動する。

暫定のスキル。詳細化を検討する点は [dev/skills/README.md](../README.md) にある。

用語の正本は `docs/ubiquitous-language/` の用語 item（1 語 1 ファイル）で、`CONTEXT.md` や用語集のファイルは
作らない。経緯は [用語を ubiquitous_term の item で管理する](../../../docs/adr/ubiquitous-term-type.md)。

## 既存の用語を読む

議論を始める前に、いまの正名と避ける綴りを読む。開発シェルを起動せずに読める。

```bash
# 語の一覧（主題ごと。英語の正名と日本語の正名）
cat docs/ubiquitous-language/index.md
# 正名と避ける綴り（frontmatter）
rg -n '^(name|name_ja|avoid):|^  - ' docs/ubiquitous-language -g '!index.md'
```

定義まで要る語は、その item の `## 定義` を読む。

## 議論の中でやること

- **食い違いを指摘する**: 利用者や文書の語が、既存の正名と違う意味で使われているか、避ける綴りで書かれていたら、
  その場で指摘してどちらの意味かを訊く。
- **曖昧な語を研ぐ**: 1 つの語が 2 つのものを指していたら、分けるかどうかを訊き、正名を提案する。
- **具体的な場面で確かめる**: 語の境界は、境界に当たる場面を作って確かめる（「この場合は A と呼ぶか、B と呼ぶか」）。
- **既存の語で足りるなら足さない**: 新しい語を提案する前に、一覧に同じ概念の語が無いかを確かめる。
- **決まったらその場で書く**: 語が決まるたびに台帳へ 1 行足す。議論の最後にまとめて書かない。

## 語にするもの、しないもの

- 語にするのは、文書管理と品質の考え方に固有の概念。一般の技術用語は入れない。
- 用語は、mitodoke を適用する様々な製品で共通に使う語として決める。特定の製品の機能の名前は入れない。
- `docs/model.yaml` が定義する relation・フィールド・値は語にしない。`model.yaml` に定義が無い名前だけを語にする。
- 既存の語の正名や避ける綴りを変える決定も、台帳に書く（slug を既存の item と同じにする）。

## 台帳へ書く

書式と置き場所は [references/ledger-format.md](references/ledger-format.md)。1 語を 1 行で書き、状態は `未起票` にする。
`section` は `docs/model.yaml` の `ubiquitous_term` の enum から選び、合う値が無ければ空欄のまま利用者に訊く。

## 議論を終えるとき

台帳に残っている `未起票` の語を数えて、利用者へ伝える。「台帳に N 語ある。PR を作る前に `/term-apply` で item にする」
と 1 文で言う。このスキルは `docs/ubiquitous-language/` に書き込まない。
